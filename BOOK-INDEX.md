## What this book is

*Microsoft Sentinel Operations* is a platform-operations handbook, not a query-language primer. DEH Part 25 already teaches KQL syntax against the Sentinel/Defender table catalog — the pipe model, `where`/`join`/`summarize`, time-window functions, join-strategy hints — and DEH Part 23 already frames the Sigma-vs-native-query tradeoff that produces a Sentinel scheduled rule in the first place. This book assumes both. It starts where DEH Part 25 stops: once a KQL query exists, what does it take to run it as a durable, monitored, cost-accounted piece of a production SOC platform — the workspace it lives in, the rule type that hosts it, the incident it feeds, the automation that responds to it, the tier it's billed under, and the portal (there are, as of this writing, two, with one being retired) an analyst uses to see the result.

The book has the same two-layer split DEH uses — **platform layer** (what Sentinel/Defender actually is, how data moves through it, what a feature does and doesn't do) and **operations layer** (what a SOC builds and runs on top of the platform: rules, automation, dashboards, tuning) — because conflating "how ingestion billing works" with "how to write a good analytics rule" produces the same shallow-breadth problem DEH's own architecture notes name as a defect to avoid.

**Honesty constraint, stated once here and enforced throughout by `STYLE-GUIDE.md` §9:** this book's author has no real Microsoft Sentinel tenant, Log Analytics workspace, or Defender portal license in their environment (contrast the home-lab Linux/Proxmox environment DEH draws real captured evidence from). Every claim in this book is sourced from Microsoft's own public documentation or stated as a conceptual/architectural illustration — never as a captured screenshot or a validated-in-production result. This book uses **two** of DEH's four evidence classes almost exclusively: `OFFICIAL REFERENCE` (Microsoft Learn diagrams, screenshots, and documented behavior, cited) and `CONCEPTUAL` (architecture/data-flow sketches with no claim of being captured from a real system). `CONTROLLED LAB EXAMPLE` and `REAL LAB EXAMPLE` stay defined in `STYLE-GUIDE.md` for series consistency and for the day a real tenant exists, but no unit in this book's initial release may use either tag — see `STYLE-GUIDE.md` §9.4 for what happens if a reviewer is tempted to.

## Multi-level content model

Adapted from DEH's six content tags for a platform-operations audience. Full rationale for each rename in `STYLE-GUIDE.md` §7; summary here:

- `[CONCEPT]` — foundational "what and why" for a platform feature or architectural component, no assumption the reader acts on it directly. Unchanged from DEH.
- `[ANALYST]` — triage- and investigation-facing: what an incident in the unified queue means, what an entity graph tells you, when to pull a watchlist, how to read a workbook. Unchanged label; scope shifted from "alert response" to "unified-incident-queue investigation."
- `[SENTINEL ENGINEER]` — **renamed from DEH's `[DETECTION ENGINEER]`.** Builds and tunes the platform's detection *and response* logic: analytics rule authoring, entity mapping, watchlist curation, automation rule and playbook logic. Broader than DEH's tag on purpose — this book's "rule builder" role also builds the automation and reference data DEH doesn't cover, and a single narrower tag would force artificial splitting.
- `[THREAT HUNTER]` — hypothesis-driven exploration inside Sentinel/Defender specifically: hunting queries, bookmarks, notebooks, UEBA-anomaly pivots. Unchanged from DEH.
- `[ENGINEERING]` — the plumbing a rule or dashboard runs on top of: workspace architecture, connectors, Data Collection Rules, table tiering, retention, ingestion cost and performance. Unchanged from DEH — this tag already meant "the platform underneath the rule," which is most of what this book is about.
- `[SOC MANAGEMENT]` — licensing/commitment-tier decisions, staffing for platform operations, the Azure-portal-retirement migration as a program-management problem, risk-acceptance on retention and tuning tradeoffs. Unchanged from DEH.

Only one tag was renamed (`[DETECTION ENGINEER]` → `[SENTINEL ENGINEER]`); the other five carry their DEH meaning forward directly, because this book's operations focus maps cleanly onto DEH's existing telemetry/analytic-layer split — it just runs that split through one vendor's platform in detail DEH deliberately left to it (DEH Part 25's own scope note excludes "Sentinel analytics-rule YAML, CI/CD wrapper metadata, or rule-repository structure," naming this book's Part 7 as the place that detail belongs).

## Recurring callout features

This book carries forward all eight of DEH's callout templates (**Detection Autopsy**, **Hunter's Note**, **Engineering Reality**, **Blind Spot**, **False Positive Trap**, **Detection Test**, **SOC Management View**, **What Would Change My Mind** — exact templates unchanged, see `STYLE-GUIDE.md` §6) and adds a ninth, **PRODUCT VERSION NOTE**, built in the same blockquote shape, for the one failure mode DEH's callout set doesn't need to name because Sigma/KQL syntax drifts slowly: a SaaS platform whose rule types, portal, and pricing tiers change on a vendor's own release cadence, sometimes with a hard retirement date already published. Full template and worked example in `STYLE-GUIDE.md` §6.9.

Callout density differs from DEH's typical mix: expect **PRODUCT VERSION NOTE** and **Engineering Reality** to be the highest-frequency boxes in this book (most parts touch at least one feature that is preview, recently renamed, or on a published deprecation timeline), and **Detection Autopsy**/**Detection Test** to appear only in the parts that discuss actual rule or automation logic (Parts 4, 5, 13, 14), not throughout — this book is not primarily a rule-writing book the way DEH is.

## Production model

Same mandatory front matter as DEH (`author`, `reviewer`, `status`, `last_validated`, `depends_on`) and the same author≠reviewer separation-of-duties rule. Two additions specific to this book:

- Every unit's `depends_on` may reference a DEH part directly using the form `DEH-23`, `DEH-25`, etc., alongside this book's own part numbers, so a reader can trace a cross-reference without guessing which book a bare number belongs to.
- Because this book has no lab evidence to draw on, every reviewer sign-off for a unit citing a specific platform behavior (a limit, a default, a retirement date, a pricing figure) must record which Microsoft Learn URL was checked and the date it was checked — a lighter-weight version of DEH's `REFERENCES.md` citation requirement, made mandatory here specifically because `OFFICIAL REFERENCE` is this book's load-bearing evidence class rather than one of four options.

## Key structural decisions and provenance

1. **18 parts, not the full 20 the brief's range allowed.** This book's scope is one vendor's platform-operations layer, not a full detection-engineering curriculum — DEH needed 48 parts to cover telemetry sources, query languages, and analytic technique across every domain; this book borrows all of that from DEH by reference and only has to cover what's genuinely platform-specific. Padding to 20 with a thinner split (e.g., breaking Automation into three parts instead of two) would repeat DEH's own named V1 defect of breadth without matching depth.
2. **Sections F (Defender XDR Convergence) and the Part 2/16 portal split are the parts most likely to date fastest**, because they describe an active platform migration with a published hard retirement date (March 31, 2027, for Sentinel-in-Azure-portal) sitting inside the book's planning horizon. Every unit in these parts carries a mandatory PRODUCT VERSION NOTE, not an optional one — recorded here so a future editor doesn't read the density as author inconsistency.
3. **UEBA (Part 11) and AI-Assisted Operations (Part 12) are split**, even though both are "Microsoft's machine-learning layer on top of Sentinel data," because UEBA is a mature, priced-at-zero-extra-cost, multi-year GA feature with a stable table schema, while Security Copilot / agentic tooling is genuinely new ground with no DEH precedent and the fastest-changing surface in the entire book. Merging them would force one PRODUCT VERSION NOTE density onto a part that mostly doesn't need it.
4. **No part in this book attempts to re-teach KQL.** Every part that includes a code example either points at DEH Part 25 for syntax or shows only the Sentinel-specific extension DEH Part 25 doesn't cover (a watchlist lookup, an entity-mapping expression, a data-lake KQL job). This is the direct implementation of the brief's instruction to cross-reference rather than re-teach, applied as a structural rule, not a per-part judgment call.
5. **The honesty constraint (no real tenant) is stated once, prominently, in Part 1 and in this file's own "What this book is" section — not repeated as a disclaimer in every part.** `STYLE-GUIDE.md` §9 carries the enforcement mechanism (which evidence-class tags are actually permitted); repeating the constraint in prose in all 18 parts would be exactly the kind of filler the voice guide bans elsewhere in the series.
